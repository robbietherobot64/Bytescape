## 1. Overview

The notifications screen is the user's activity center: a reverse-chronological feed of every event that concerns them — likes, reposts, follows, replies, mentions, and profile comments. FR-25 specifies that notifications are generated by the AppView consumer when processing firehose events (and by app-DB events for `profile_comment`), stored in the `notifications` table as application state, and delivered in real-time via SSE or WebSocket.

The screen serves one audience — the signed-in user — with three affordance tiers:

| Viewer | Sees | Can do |
|---|---|---|
| Authenticated user | Full notification feed | Filter by type, mark read/unread, mark all read, click to navigate |
| Unauthenticated visitor | Login redirect | Route to `/notifications` triggers auth gate |

### 1.1 Notification types

| Type | Trigger | Icon | Click target |
|---|---|---|---|
| `like` | Someone liked your post | ❤️ | The post (feed or profile) |
| `repost` | Someone reposted your post | 🔁 | The post |
| `follow` | Someone followed you | 👤 | Their profile (`/@{handle}`) |
| `reply` | Someone replied to your post | 💬 | The reply thread |
| `mention` | Someone mentioned you in a post | @ | The post |
| `profile_comment` | Someone posted on your wall or left a visitor-counter comment | 📝 | Your profile wall section |

### 1.2 Data sources (v2)

| Data | Location | Notes |
|---|---|---|
| Notification records | `notifications` table (app DB) | `id`, `user_did`, `type`, `actor_did`, `subject_uri`, `read`, `created_at` |
| Actor identity (name, avatar, handle) | `appview_profiles` | JOIN on `actor_did` for display enrichment |
| Subject post text (preview) | `appview_posts` | JOIN on `subject_uri` for post snippet; NULL for follow notifications |
| Muted accounts | `muted_accounts` table | Notifications from muted actors are excluded from the query |
| Unread count | `notifications` table | `COUNT(*) WHERE user_did = ? AND read = FALSE`; cached client-side, updated by SSE/WebSocket events |
| Real-time updates | SSE or WebSocket | New notifications push to client; unread count updates atomically |

### 1.3 Dual PDS note (AD-01b)

Notifications are PDS-agnostic application state. Both Bytescape-hosted (`did:web`) and Bluesky-hosted (`did:plc`) users receive notifications identically — the `notifications` table keys on `user_did`, not on PDS type. The AppView consumer generates notifications from firehose events regardless of which PDS originated the action.

| | Bytescape-hosted (`did:web`) | Bluesky-hosted (`did:plc`) |
|---|---|---|
| Receiving notifications | Identical — app DB query | Identical |
| Notification generation | Firehose consumer + app-DB triggers | Same |
| Actor resolution | `appview_profiles` lookup by DID | Same |

Frontend consequence: the notification UI is PDS-agnostic. No special handling for user class anywhere in this screen.

### 1.4 Frontend stack (kept)

React 19 + Vite + TypeScript with the v1 patterns retained per the 2026-08-09 stack decision: `useState`/`useEffect`, localStorage caching, and the custom DOM event bus (`bytescape:notificationsUpdated`, `bytescape:toast`, `bytescape:viewProfile`). The `NotificationBell` in the TabBar maintains its own polling/SSE subscription for the unread badge; the full screen takes over the connection when mounted.

## 2. v1 Salvage Assessment

Verdicts: **KEEP** (reuse as-is or with trivial touch-ups), **REFINE** (keep concept and most code, improve), **REWORK** (keep concept, rebuild internals), **DROP** (obsolete; mine for parts), **DEFER** (concept preserved intact, design work postponed to Phase 2).

Summary: **0 KEEP · 1 REFINE · 0 REWORK · 0 DROP · 0 DEFER** — v1 had only the bell dropdown; the full screen is new construction. The bell's dropdown logic is the only salvageable artifact.

| # | File (lines) | Verdict | One-line rationale |
|---|---|---|---|
| 1 | `NotificationBell.tsx` (199) | **REFINE** | Unread badge (9+ cap), dropdown with per-item + mark-all read, 30s polling — works. Refinement: move ~115 lines of inline styles to CSS classes; pause polling when tab is hidden; notification click navigates to the relevant post/profile instead of staying in the dropdown; dropdown becomes a preview (last 5) that links to the full screen |

### 2.1 v1 defects fixed by this spec (evidence-grounded)

1. **No full notification screen** — v1 has only a dropdown preview in the bell icon. Users who miss the dropdown or want to browse older notifications have no surface. Fixed: full `/notifications` screen with pagination.
2. **Inline styles in NotificationBell** — ~115 lines of inline styles (the dropdown panel, notification items, badge). Moved to CSS classes so theming and responsive rules apply.
3. **Polling never pauses** — 30s `setInterval` runs even when the tab is hidden. Fixed: `document.visibilitychange` listener pauses polling when hidden, resumes on visible.
4. **Notification click doesn't navigate** — clicking a notification in the dropdown closes the dropdown but doesn't route to the relevant post/profile. Fixed: every notification click navigates (see 6.1).
5. **No type filtering** — all notification types are lumped together. Fixed: filter bar with type chips (section 4.2).
6. **No real-time delivery** — v1 uses 30s polling only. Fixed: SSE/WebSocket subscription with polling fallback.

## 4. Component Breakdown

### 4.1 Screen shell

**`NotificationsScreen` (NEW)**
- Purpose: mount the notification feed, manage filter state, coordinate real-time updates, handle the SSE/WebSocket subscription lifecycle.
- Props: none (route-level component; viewer context from auth).
- State: `notifications: NotificationItem[]`, `unreadCount`, `activeFilter: NotificationType | 'all'`, `status: loading | error | ready`, `cursor` (pagination), `hasMore`, `loadingMore`.
- Loads via `GET /api/notifications?type={filter}&cursor={cursor}&limit=20`.
- On mount: establishes SSE/WebSocket subscription for real-time notification pushes. On unmount: tears down subscription, hands real-time back to the TabBar bell.
- Delegates to `NotificationFilterBar` + `NotificationList`.
- Dispatches `bytescape:notificationsUpdated` on incoming real-time events so the TabBar bell badge stays in sync.

### 4.2 Filter bar

**`NotificationFilterBar` (NEW)**
- Purpose: type filter chips + "Mark all read" button.
- Props: `activeFilter`, `onFilterChange`, `onMarkAllRead`, `unreadCount`.
- Filter chips: All, ❤️ Likes, 🔁 Reposts, 👤 Follows, 💬 Replies, @ Mentions, 📝 Comments.
- "All" is the default. Selecting a chip filters the list (API re-fetches with `?type={filter}`).
- "Mark all read" button: calls `POST /api/notifications/read-all`, optimistically sets all items to read, resets unread count to 0, dispatches `bytescape:notificationsUpdated`.
- Sticky on scroll: `position: sticky; top: 0` with the app's `--bg-primary` background to avoid content bleed-through.
- Accessibility: chips are `role="tab"` in a `role="tablist"`, `aria-selected` on the active chip, `aria-label` on the mark-all-read button ("Mark all notifications as read").

### 4.3 Notification list

**`NotificationList` (NEW)**
- Purpose: render grouped notification items with day separators, loading states, empty state, and load-more.
- Props: `notifications`, `status`, `hasMore`, `loadingMore`, `onLoadMore`, `activeFilter`.
- Grouping: items are grouped by day — "Today", "Yesterday", "This week", "Older" — with separator headers. Within each group, items are reverse-chronological.
- Each item renders via `NotificationItem`.
- Load-more: `> LOAD MORE NOTIFICATIONS` button (retro CTA pattern, consistent with the feed spec) + optional infinite-scroll sentinel.
- Subcomponents:

**`NotificationGroup`** — day separator header + list of `NotificationItem` components.

### 4.4 Notification item

**`NotificationItem` (NEW)**
- Purpose: a single notification row — icon, actor avatar, description text, subject preview, timestamp, unread dot.
- Props: `notification: NotificationItem`, `onRead(id)`, `onNavigate(notification)`.
- Shape:
  ```
  [unread dot] [actor avatar] [type icon] [actor handle + action text] [subject preview snippet] [relative timestamp]
  ```
- Unread indicator: a small accent-colored dot (`--accent`, 8px) left of the avatar. Dot disappears on read (click or mark-all-read).
- Actor avatar: from `appview_profiles`. Initials fallback if no avatar URL.
- Type icon: the emoji for the notification type (section 1.1), rendered left of the text.
- Action text: e.g., "liked your post", "followed you", "replied to your post", "mentioned you", "commented on your profile".
- Subject preview: truncated to one line (48 chars + ellipsis) from `appview_posts.text`. For `follow` notifications, no preview — just the action text.
- Timestamp: relative ("2h", "3d", "1w") using the same formatter as feed post cards.
- Click target: the entire row is clickable. Clicking marks the notification as read (optimistic + API call `POST /api/notifications/{id}/read`) and navigates to the target (section 6.1).
- Hover state: `background: rgba(0,255,65,0.05)` (consistent with feed post card hover).
- Accessibility: `role="article"`, `aria-label` describing the full notification ("@mika liked your post 2 hours ago"), `tabIndex={0}`, Enter/Space triggers navigation.

### 4.5 TabBar bell (existing, refined)

**`NotificationBell` (REFINE from v1)**
- Purpose: unread badge in the TabBar + dropdown preview of recent notifications.
- Kept from v1: unread badge (9+ cap), dropdown with per-item + mark-all read, 30s polling fallback.
- Changed:
  - Dropdown shows last 5 notifications (preview), with a "See all notifications →" link at the bottom that navigates to `/notifications`.
  - Clicking a notification in the dropdown navigates to the target (same as the full screen).
  - Inline styles (~115 lines) moved to CSS classes.
  - Polling pauses when `document.hidden` is true.
  - When the full `NotificationsScreen` is mounted, the bell's SSE/WebSocket subscription is handed off to the screen to avoid duplicate connections. The bell re-establishes its own subscription when the screen unmounts.
  - Badge count updates in real-time from the same SSE/WebSocket stream.

### 5.6 Edge cases

| Case | Behavior |
|---|---|
| Notification for deleted post | Subject preview shows "[post unavailable]"; click navigates to the feed (no crash, no empty state) |
| Notification for deactivated/suspended actor | Actor avatar shows initials fallback; handle shows "[account unavailable]"; click is a no-op |
| Very long actor handle | Truncated with ellipsis at 24 chars in the item row |
| Batch notifications (e.g., 5 likes on one post) | **Phase 2: collapse into "5 people liked your post" with stacked avatars.** v2.0 renders individual items. Open question OQ-1 |
| Notification during filter switch | Filter change triggers a new API fetch; stale results from the previous filter are cleared immediately (no flash of wrong data) |
| SSE/WebSocket reconnect | On connection drop: switch to 30s polling, show a subtle "Reconnecting…" banner below the filter bar. On reconnect: resume SSE/WebSocket, dismiss banner, fetch any missed notifications |
| Mark-all-read while filter is active | Marks ALL notifications as read (not just the filtered type). The filtered view updates to show no unread dots |

## 6. Interactions

### 6.1 Notification click → navigate

| Notification type | Click target | Navigation |
|---|---|---|
| `like` | The liked post | `/` (feed) with the post's URI as a deep-link anchor, or `/@{handle}` profile feed if the post is an archive post |
| `repost` | The reposted post | Same as `like` |
| `follow` | The follower's profile | `/@{handle}` of the actor |
| `reply` | The reply thread | Thread view: `/post/{uri}` (or feed scroll-to with reply expansion) |
| `mention` | The mentioning post | Same as `reply` |
| `profile_comment` | The user's profile wall | `/@{handle}` with wall section scroll anchor |

Click flow:
1. Optimistic mark-as-read: remove unread dot immediately, decrement unread count.
2. API call: `POST /api/notifications/{id}/read` (fire-and-forget; rollback on failure — re-show dot, increment count).
3. Navigate: `navigate(target)` using the router.

### 6.2 Mark all read

1. Click "Mark all read" in the filter bar.
2. Optimistic: all unread dots disappear, unread count → 0, dispatch `bytescape:notificationsUpdated` with count 0.
3. API call: `POST /api/notifications/read-all`.
4. On failure: rollback — re-fetch the notification list to restore correct read/unread state.

### 6.3 Filter change

1. Click a filter chip.
2. Clear current list, show loading skeletons.
3. API call: `GET /api/notifications?type={filter}&limit=20`.
4. Render results. If empty, show filtered-empty state (5.4).

### 6.4 Load more

1. Click `> LOAD MORE NOTIFICATIONS` or scroll past the infinite-scroll sentinel.
2. API call: `GET /api/notifications?type={filter}&cursor={cursor}&limit=20`.
3. Append results to the existing list (dedup by `id`).
4. If no more results, hide the button and sentinel.

### 6.5 Real-time notification arrival

1. SSE/WebSocket delivers a new notification event.
2. Prepend the new notification to the top of the list (with unread dot).
3. Increment unread count.
4. Dispatch `bytescape:notificationsUpdated` so the TabBar bell badge updates.
5. If the active filter is not "all" and the new notification's type doesn't match, still increment the count but don't add to the visible list.
6. Optional: subtle slide-in animation (200ms ease-out from top, `prefers-reduced-motion` respected).

### 6.6 Keyboard

| Key | Action |
|---|---|
| `j` / `↓` | Focus next notification item |
| `k` / `↑` | Focus previous notification item |
| `Enter` / `Space` | Activate focused notification (navigate) |
| `r` | Mark focused notification as read/unread (toggle) |
| `Shift+A` | Mark all as read |
| `1`–`7` | Switch to filter chip by position (All=1, Likes=2, …) |
| `Tab` | Cycle through filter chips and notification items |

### 6.7 Accessibility

- `aria-live="polite"` region on the notification list for new-arrivals announcement: "New notification: @mika liked your post".
- `aria-live="assertive"` on the unread count badge in the TabBar (screen readers announce count changes).
- Notification items are `role="article"` with `aria-label` containing the full notification text.
- Filter chips are `role="tab"` in a `role="tablist"`.
- Mark-all-read button has `aria-label="Mark all notifications as read"`.
- Focus trap: when the screen mounts, focus moves to the filter bar. When navigating away, focus returns to the trigger (bell icon).
- `prefers-reduced-motion`: disables the slide-in animation for new notifications; uses instant appearance instead.

## 8. Open Questions

| # | Question | Default if unresolved | Impact |
|---|---|---|---|
| OQ-1 | **Batch notification collapsing.** Should multiple notifications of the same type on the same subject be collapsed (e.g., "5 people liked your post" with stacked avatars)? Bluesky's default client collapses; Facebook shows individual items. | **Individual items** (v2.0 ships without collapsing). Collapsing is a Phase 2 optimization for users with high engagement | Component design (NotificationItem would need a batch variant); API grouping logic |
| OQ-2 | **SSE vs. WebSocket.** FR-25 says "SSE or WebSocket." SSE is simpler (unidirectional, no upgrade handshake, works through more proxies). WebSocket enables bidirectional (future: mark-as-read from the push channel). | **SSE** (simpler, sufficient for push-only notifications). WebSocket is a future upgrade path | Transport layer; reconnect logic |
| OQ-3 | **Notification grouping by day vs. time.** The spec groups by "Today / Yesterday / This Week / Older." Should "This week" collapse further into "This month" after 7 days, or is the four-tier grouping sufficient? | **Four-tier grouping** (Today / Yesterday / This Week / Older) | Display logic only |
| OQ-4 | **Notification sound.** Should new notifications trigger an audible alert? Modern social apps do; the terminal aesthetic could use a subtle beep. | **No sound** (Phase 2 opt-in).
